# Setmio 健身规划 App 完整方案（产品 + 算法 + 架构 + 路线图 + 本次实施范围）

> 依据：三路网络研究（Apple Watch/HealthKit 能力边界、GLP-1 药物说明书与监管、训练科学/营养技术/竞品）+ 一轮架构设计，2026-10-09。标注"待确认"的事实在实施时核对。

## Context（为什么做、做成什么样）

用户要做一个 iOS + Apple Watch 的健身规划 App（仓库 `Setmio`，目前只有 README）。核心诉求：
- 接 Apple Watch 实时数据，分析压力/恢复，自动规划训练强度并逐步加量（渐进超负荷），也支持手动记录强度。
- 接体重秤等设备数据；后续加入热量摄入计算（拍照一键识别热量）。
- 全部接入 AI。
- 接入替尔泊肽等减肥针：规划怎么打、根据体重变化速度和各类数据判断是否加量；到达目标体重后何时减量、如何减量。
- 训练中：动作指导、倒计时、次数计时、组间休息规划。
- 日常：步数、日常消耗热量、精细热量记录，统一分析。

已和用户确认的决策（2026-10-09）：

| 目标市场 | 中国大陆为主（中文、中餐食物库、国内体脂秤、国内药品名 穆峰达/诺和盈） |

## 1. 产品定位与边界

一句话：**一个 Apple Watch 原生的"力量训练自动调节 + 能量平衡 + 减肥针周期管理"个人教练**，所有数据（手表、秤、饮食、针剂、主观感受）汇到一个模型里做统一分析。

竞品空隙（研究结论）：目前没有一个 Apple Watch 原生 App 同时做到 ①按 HRV 恢复度调节的 RIR/e1RM 自动渐进 ②按摄入+体重趋势反推的自适应 TDEE ③GLP-1 周期感知（保肌/蛋白/剂量计划）。最接近的是 Bevel（恢复+营养+力量，但自动调节未公开）、MacroFactor 套装（TDEE+渐进，无恢复度/GLP-1）、Preserve/StayBuilt（GLP-1+力量+蛋白，无自适应 TDEE）、Apple 自带 Readiness（仅 Series 12/Ultra 4，待确认）。空隙真实但在收窄。

边界（自用阶段也遵守，避免以后返工）：
- 减肥针：App **记录、提醒、按既定方案（医生/说明书）推进、给出"是否该加量/减量"的分析和建议**；不做"处方"。所有建议都标注"与医生确认"。公开上架时此模块退化为"记录+提醒+医生方案执行"（App Store 1.4.2）。
- AI：规则引擎负责"算"，LLM 负责"看图识别、解释、问答、写总结"。规则可解释、可回放。

## 3. 数据接入层

### 3.1 Apple Watch / HealthKit（能拿到什么、拿不到什么）
**能读到的类型（HealthKit）**
| 类别 | 标识符 | 采样特性 / 注意 |
|---|---|---|
| 心率 | `heartRate`（带 sedentary/active 上下文）、`walkingHeartRateAverage`、`heartRateRecoveryOneMinute` | 旧表静止时约每 5 分钟一次、训练中约每 5 秒；Series 12/Ultra 4 全天每 5 秒 |
| 静息心率 | `restingHeartRate` | **当天值会被系统反复修正**，须在固定时间冻结，或改用睡眠期心率自算 |
| HRV | `heartRateVariabilitySDNN`；iOS 27 新增 `heartRateVariabilityRMSSD`（手表是否写入待验证）；`HKHeartbeatSeriesSample` 心搏序列可自算 RMSSD | 旧表默认约每 2–5 小时一次（开启房颤历史约 15 分钟）；Series 12/Ultra 4 静止时最快每 5 分钟；**无 API 主动触发测量**，可引导做 1 分钟正念呼吸得到一次读数 |
| 夜间生命体征 | `respiratoryRate`、`appleSleepingWristTemperature`（Series 8+，每晚一值，需睡眠专注，只读）、`oxygenSaturation` | Vitals 的"超出范围"标记本身不暴露，要自己算 |
| 睡眠 | `sleepAnalysis`（inBed/awake/core/deep/REM）、`appleSleepingBreathingDisturbances` | watchOS 26 睡眠分数无 HealthKit 类型 |
| 活动 | `stepCount`、`activeEnergyBurned`、`basalEnergyBurned`、步行/跑步各项、`vo2Max`、`physicalEffort`(METs) | 活动能量误差约 28% MAPE，只作弱先验 |
| 训练 | `HKWorkout`、`workoutEffortScore`/`estimatedWorkoutEffortScore`（0–10，力量训练需手动评分，用 `relateWorkoutEffortSample` 关联） | **Training Load 无 HealthKit 类型**，须按 7 天/28 天自算 |
| 体成分 | `bodyMass`、`bodyMassIndex`、`bodyFatPercentage`、`leanBodyMass` | 无肌肉量/骨量/水分类型 |
| 用药 | iOS 26+ `HKUserAnnotatedMedicationQueryDescriptor`、`HKMedicationDoseEvent`（按药品授权，只读） | 可作减肥针记录的补充来源 |
| 区间 | iOS 27 训练心率区间（`HKWorkoutZoneGroup`，实时回调） | 自定义区间需自行保存 |

**拿不到的**：压力值、Apple Readiness（0–10，仅 Series 12/Ultra 4，未对第三方开放）、Training Load、睡眠分数、Vitals 标记；训练中光学传感器的 RR 间期；Workout Buddy 无 API。

**实时训练能力**
- watch 端 `HKWorkoutSession` + `HKLiveWorkoutBuilder`：后台常驻、实时心率流、后台触觉；需 `workout-processing` 后台模式；同一时间只能有一个会话；CPU 过高会被挂起。
- 镜像到 iPhone（watchOS 10+）：`startMirroringToCompanionDevice()`，`sendToRemoteWorkoutSession(data:)` 双向传自定义数据。iOS 26 起 iPhone 也能单独开会话（需蓝牙心率带）。
- WorkoutKit **没有"次数目标"**，力量训练的组/次模型要自建；训练结束写入 `HKWorkout(.traditionalStrengthTraining)` + effort score，让 Apple 的训练负荷/Smart Stack 认可我们的训练。
- 传感器：`CMBatchedSensorManager` 800 Hz 加速度 / 200 Hz device motion，每秒一批，**需活动训练会话**，Series 8+。

**后台投递**：需 `com.apple.developer.healthkit.background-delivery` entitlement；iOS 多数类型最快每小时一次，watchOS 几乎都是每小时；observer 回调必须调用 completion（连续 3 次失败即停止投递）；设备锁定时读取可能失败。策略：App 前台时用 `HKAnchoredObjectQuery` 增量拉取（按类型持久化 anchor），observer 只当"推一把"。

**Apple 规则要点**：5.1.3 健康数据不得存 iCloud、不得用于广告/数据挖掘；1.4.1 需披露评分方法并提醒咨询医生；1.4.2 剂量计算器限制；5.1.1(ix) 医疗类 App 应由法人而非个人提交；需要 `NSHealthShareUsageDescription`/`NSHealthUpdateUsageDescription` 与隐私清单；摄像头/深度数据不得用于分析广告（5.1.2(vi)）。

### 3.2 体重秤
- **v1 只经 HealthKit 读取** `bodyMass`、`bodyFatPercentage`、`leanBodyMass`，零设备代码即可覆盖：小米（米家/Zepp Life，仅主账号）、华为体脂秤 3 Pro（华为运动健康单向同步，体脂偶尔不同步）、有品 PICOOC、Renpho、Eufy、Withings。云麦/Keep 秤是否写入 Apple Health 未证实。
- 体脂率只当"趋势"用（BIA 噪声大），不参与每日计算。
- v2 可接 Withings 公共 API（OAuth2 + webhook，免费 120 req/min）。
- **不做**私有 BLE 协议直连（小米加密/广播协议、型号频繁变动、openScale 代码 GPL 风险）。

### 3.3 手动记录
- 每组：重量、次数、RPE/RIR（二选一界面，内部统一为 RIR）；每次训练后：酸痛、泵感、关节痛 1–4 分（RP 式反馈）。
- 每日：主观状态（睡眠感受、动力、酸痛 1–5），早晨称重，针剂、副作用。

### 3.4 饮食（拍照识别）
研究结论：多模态 LLM 看混合餐能量误差中位数约 33–36%（Opus/Sonnet 4.6 在美/日餐数据集），包装食品 14–19%；所有模型对大份量系统性低估；有参照物能改善。专用 App（Cal AI 等）在 NIH 对照试验里平均低估约 33%。
设计：
1. 第一遍：LLM 识别菜品组成（中餐按"菜"拆：番茄炒蛋、米饭、汤）；
2. 第二遍：用户确认份量（碗/份/克 选项 + 参照图），**炒菜必问"用油多/少"**；
3. 输出热量**区间 + 置信度**，而不是一个数；
4. 包装食品走条码（GS1 中国无公开营养 API，只能拿到品名）→ 营养成分表 OCR；
5. 记录用户修正，做按人的偏差学习；不做无验证数据的全局偏差修正。
食物库：自用阶段用**中国食物成分表（第 6 版）官方查询平台（约 1300 种，非商业免费）** + USDA FDC（CC0）作兜底；商业化时接薄荷健康开放平台（150 万+食物、条码、图像识别、份量估计，API Key 制，价格未公开）。不要把 Open Food Facts（ODbL）混入私有库。

### 3.5 减肥针记录
记录项：药物（通用名 + 品牌，如 替尔泊肽/穆峰达、司美格鲁肽/诺和盈、玛仕度肽/信尔美、利拉鲁肽、口服司美/口服 orforglipron）、规格（单剂量笔 / 多剂量笔 4 针 / **瓶装或未验证来源**）、剂量 mg、注射时间、部位（腹部/大腿/上臂，自动轮换提示）、笔库存与**在用有效期**（替尔泊肽单剂量笔常温 ≤30 °C 21 天、多剂量笔首用后 30 天或 4 针；诺和盈首用后 6 周；US Wegovy 28 天）、冷链异常（冻过/过热）、副作用（恶心/呕吐/便秘/腹泻/乏力 0–3 级）、漏针。iOS 26+ 可读 Health App 用药记录作补充来源。
未验证来源（海淘/"孟替"瓶装）的产品：允许记录但打"未验证来源"标签，**不提供计划模板、不做体积/单位换算**，显示 WHO/药监假药风险提示。

## 4. 核心算法

### 4.1 恢复/压力评分（Readiness）
Apple 不提供"压力值"（watchOS 27 的 Readiness 0–10 只在 Series 12/Ultra 4，是否经 HealthKit 暴露待确认）。自算，方法与 HRV4Training / Athlytic / Oura 一致：
- 指标统一：HRV 每人只用一种（iOS 27 若有 RMSSD 用 RMSSD，否则 SDNN），换源重建基线。
- 基线：个人最近 60 天均值/标准差，至少 14 天数据后才出分。
- 输入（每天早上，按睡眠窗口计算）：`hrv`=睡眠期 ln(HRV) 均值；`rhr`=睡眠最低/平均心率；`sleep`=睡眠时长 + 3 晚均值 + 14 天欠债；`rr`、`temp`=呼吸率、腕温偏差（生病标志）；`acwr`=7 天负荷/28 天负荷，负荷=自评强度(0–10)×分钟；`subj`=主观酸痛/动力。
```
z_hrv  = (rolling7(hrv) - mean60) / sd60        // 正常区间 ±0.5~0.75 SD
z_hrvD = (hrv_today - mean60) / sd60             // 急性下降
z_rhr  = -(rhr_today - mean60_rhr) / sd60_rhr
s_sleep= clamp(sleep_3n / need, 0, 1.1) 映射到 -2..+0.5
s_load = acwr∈[0.8,1.2]→0；>1.5→-1.5；<0.5→0（另打"退训"标签）
S = (0.35*z_hrv + 0.10*z_hrvD + 0.15*z_rhr + 0.20*s_sleep + 0.10*s_load + 0.10*z_subj) / Σ(可用分量权重)
Readiness = clamp(65 + 15*S, 0, 100)   // ≥60 绿，45–59 黄，<45 红（普通日落在 60–70 的绿带，红需要 HRV 约 1.3 SD 以下再叠加睡眠/主观）
覆盖规则（仿 Apple Vitals）：{rhr>均值+2SD, temp 偏差>0.5 °C, rr>均值+2SD, hrv<均值-2SD} 中≥2 项 → 分数封顶 35 并标记"恢复日"
confidence = min(1, 基线天数/60) × 可用权重占比；z 值截断在 ±3，ln(HRV) 的 SD 下限 0.05
```
权重与阈值都是 `ReadinessConfig` / `ReadinessWeights` 里的可配置项（实现见 `SetmioCore/Engines/ReadinessCalculator.swift`，单元测试含 golden 用例），上线后按用户自己的"训练表现 vs 评分"回归微调。

### 4.2 训练强度自动规划（渐进超负荷 + 自动调节）
原则：**规则引擎可解释、只改今天**（Juggernaut 做法）；LLM 只负责解释文案。两种模式：自动（引擎给重量/次数/RIR）与手动（用户记 RPE/RIR，引擎据此下次调整）。
```
// 每个动作：次数区间 [lo,hi]、目标 RIR（按周期周数）、最小加重 inc（杠铃上肢 2.5kg，下肢/硬拉 5kg；哑铃按档位）
训练后：
  e1RM_set = load / pctRTS(reps, 10 - RIR)        // RTS 表：RPE10×1=100%，每 -1RPE 或 +1 rep 约 -2~3%
  e1RM_session = max(各工作组)
  若 所有组 reps>=hi 且 平均RIR>=目标 → nextLoad = load+inc, nextReps = lo   （双重渐进）
  否则 若 所有组 reps>=lo → nextLoad = load, nextReps = reps+1
  否则 failCount += 1, nextLoad = load
  若 failCount>=3 或 e1RM 连续两次下降 → 该动作减载：load*=0.90，重置 failCount
  若 inc/load > 5%（哑铃） → 改加次数不加重量
RPE 模式下次重量 = 近期 e1RM × pctRTS(目标次数, 10-目标RIR)
退让组：顶组后降 5–10%，重复到 RIR 回到顶组 RIR 为止
增肌周期：第1周 RIR3 → 第2周 RIR2 → 第3周 RIR1 → 第4周 RIR0–1 → 减载周（组数×0.5，RIR≥3）
容量：从 MEV 起（一般 8–10 组/肌群/周），每周 +1 组或按 RP 酸痛/表现表调整，封顶 MRV（18–25+）
全局减载触发：计划每 4–6 周（调查均值 5.6 周）或 ≥2 个肌群连续两次倒退 或 近 5 天≥3 天红
```
恢复度对今天的影响：绿=按计划（连续 2 天≥80 且上次 RIR 比目标高≥1 → 主项 +1 组）；黄=重量不变、目标 RIR+1、辅助项 -1 组；红=重量 -10~20% 或改技术/Zone2 日；红连续 ≥3/5 天或表现连降两次 → 提前减载。
组间休息默认：复合动作 RPE≥8 时 150–180s，RPE<8 时 120s；孤立动作 75–90s（Schoenfeld 2016、Grgic 2018、Singer 2024）。

### 4.3 能量平衡与自适应 TDEE
Apple Watch 活动能量误差约 28% MAPE（56 项研究汇总），所以 **只作弱先验**；主估计靠"摄入 − 体重趋势"反推（MacroFactor 思路）。
```
trendW[d] = trendW[d-1] + α·(W[d]-trendW[d-1])，α≈0.1；缺称重日跳过
ρ = 9440·f + 1817·(1-f) kcal/kg，f=脂肪占比（默认 0.75；减脂前 2–4 周调低；GLP-1 且不练力量时调低）
obsTDEE = mean(近 14–21 天摄入) - ρ·slope(trendW)
priorTDEE = Mifflin BMR×1.2 + k·步数 + 0.5·Apple 活动能量（重折扣）
TDEE = TDEE_prev + K·(obsTDEE - TDEE_prev)，K≈0.2–0.3/周，前 3 周更大
保护：7 天中>3 天未记饮食则暂停更新；周变化 clamp ±150 kcal；肌酸/碳水大波动/经期标"预期噪声"
目标：缺口 = 速率×体重×ρ/7，速率 0.5–1.0 %体重/周（默认 0.7%）
GLP-1 模式：蛋白 1.2–1.6 g/kg（或 1.5 g/kg 去脂体重），热量下限 女 1200/男 1800，力量训练≥3 次/周，
          预计 ≤16 周减 ≥14% 时告警（骨量风险），用力量表现作"瘦体重代理"
```

### 4.4 减肥针剂量规划辅助
定位：**执行一份既定方案（说明书阶梯或医生方案）+ 每 4 周给一次"是否该加量/维持/回退"的分析**，所有输出都是"建议与医生讨论"，App 不生成"下一针打多少"，而是显示方案里当前档位。研究结论：市面上没有任何第三方消费级 App 自行给出加量建议，全部是"用户/医生录入方案 + 提醒"或在互联网医院内由医生开具；FDA 把"用药记录+提醒"归为不监管范围，而"根据个人数据计算剂量/制定剂量计划"是医疗器械；中国 NMPA 把"用药指导/治疗计划"类软件可归三类，《互联网诊疗监管细则》禁止 AI 自动生成处方。自用阶段可以做决策辅助，但按上述框架写，公开上架时只需关闭"建议"层。

**说明书阶梯表（按药/市场版本化，内置）**
| 药物 | 阶梯 | 间隔 | 上限 | 漏针规则 | 最小间隔 |
|---|---|---|---|---|---|
| 替尔泊肽 穆峰达/Zepbound | 2.5→5→7.5→10→12.5→15 mg/周；维持 5/10/15 | 每档 ≥4 周 | 15 mg（国内 15 mg 规格暂缺，待确认） | 4 天内补打，否则跳过 | 72 h |
| 司美格鲁肽 诺和盈 | 0.25→0.5→1.0→1.7→2.4 mg/周 | 4 周 | 2.4 mg（US Wegovy HD 7.2 mg） | 国内说明书 5 天内补打；US Wegovy：距下一针 >48 h 则补打，连漏 ≥2 针考虑重新爬坡 | — |

**每 4 周评估一次的加量决策（仿中国药学会 2026 草案流程）**
```
前提：当前档位已满最小间隔 AND 当前档位 < 上限 AND 方案允许
副作用（近 2 周恶心/呕吐/腹泻最高等级）：
  无/轻（≤1）→ 可评估加量
  中/重（≥2）→ 建议维持当前档位（Wegovy 说明书：推迟 4 周；必要时与医生讨论回退）
减重速率（体重趋势 trendW）：
  4–8 周减重 <1%，或 12 周预计 <5% → "与医生讨论加量"（或评估应答不足）
  >1.0 kg/周 或 >1%/周 → "暂不加量"，提示蛋白/力量/体成分复查（草案：暂停加量并查体成分）
  0.5–1.0 kg/周 → "维持当前档位即可"
附加输入：恢复度持续偏低、力量表现下降（瘦体重代理）、摄入 <50% 正常连续 3 天 → 提示营养干预
输出：Advice{建议、依据数据、"与医生确认"} + 可导出 PDF（剂量/副作用/体重曲线）
```
**硬性规则（HardBlock）**：不翻倍补打；不超标签上限；间隔 <72 h（替尔泊肽）/<120 h（玛仕度肽）不允许记录为计划内；口服每日一片；瓶装/未验证来源不做剂量换算；连漏 ≥2 针（口服 ≥7 天）→ 提示联系医生再继续。
**红旗（中断流程，提示就医）**：持续剧烈腹痛放射至背部（胰腺炎）、持续呕吐/脱水、合并胰岛素/磺脲时低血糖症状、胆囊症状、过敏反应、情绪低落/自杀念头、颈部肿块、怀孕/备孕（替尔泊肽/利拉鲁肽停药 ≥1 月，司美 ≥2 月）、择期手术/胃镜前提示告知麻醉医生。禁忌筛查（首次设置）：MTC/MEN2 家族史、胰腺炎史、胃轻瘫。
**保肌（GLP-1 模式默认开启）**：蛋白目标可选 1.2–1.6 g/kg（美国四学会 2025）/ 1.0–1.2 g/kg 理想体重（中国草案）/ 80–120 g/日；力量训练 ≥3 次/周；热量下限 女 1200 / 男 1800；≤16 周减 ≥14% 告警；体脂秤瘦体重趋势 + 力量表现双监测（试验显示瘦体重占减重 25–40%）。

### 4.5 到达目标体重后的维持/减量策略
证据（内置到 App 的"维持模式"说明页）：
- 停药反弹：SURMOUNT-4 停替尔泊肽一年回升 14%（82% 的人回升超过减重量的 25%）；STEP 1 停司美一年回升约 2/3；BMJ 2026 荟萃：停药后约 0.4 kg/月，约 1.7 年回到基线。
- 低剂量维持：SURMOUNT-MAINTAIN（Lancet 2026）第 112 周：最大耐受剂量 −21.9%，降到 5 mg −16.6%，安慰剂 −9.9%；回升 ≥50% 的比例分别为 8% / 25% / 67%。ADA 2026：达目标后继续用药，维持剂量不必是最大剂量。
- 减停方式（中国药学会 2026 草案示例）：按档位 2.4→1.7→1.0→0.5→0.25，每档 4 周；或拉长间隔 7→10→14→21 天，每档 4 针；拉长间隔时核对多剂量笔在用有效期；回升达减重量 25% 时主动召回。
App 逻辑：
```
触发：trendW 达目标 ±1% 且稳定 2–4 周 → 进入"维持决策"
展示三条路径（由用户与医生选定，App 只执行）：
  A 继续当前档位（证据：继续用药维持最好）
  B 降档维持（如替尔泊肽 →5 mg；司美 →1.7 mg）
  C 逐步减停（档位递减 或 间隔拉长），每步 4 周
执行中监测：每周体重趋势；回升 ≥ 减重量 25%（或 4 周回升 >2%）→ 提示回到上一档并联系医生；
          间隔拉长时提示笔的在用有效期；副作用好转/恶化记录
停药后：进入"反弹监测"6–12 个月，持续称重与力量训练计划，蛋白目标不变
```

## 5. AI 层（Claude / 可替换）
- **职责划分**：规则引擎算数值；LLM 做 ①拍照识菜与初估 ②把引擎决策翻译成人话（"为什么今天减 10%"）③教练问答（带入近 30 天结构化摘要）④周报 ⑤自由文本饮食解析（"两碗米饭+番茄炒蛋"→结构化）。
- **模型**：默认 `claude-opus-5-5`（混合餐识别用能力最强的；研究显示 Opus 系列对复杂餐最准），`claude-haiku-5-5` 可作用户自选的省钱档。思考用 adaptive，`output_config.effort` 按任务调；结构化输出用 `output_config.format`；菜品识别用 strict 工具 schema。
- **调用方式**：iOS 不直连（无官方 Swift SDK，且密钥不能放客户端）；走一个极小的 TypeScript 代理（Cloudflare Workers / Vercel / 自建）用 `@anthropic-ai/sdk`，做鉴权、限流、照片脱敏（去 EXIF、裁剪）、日志。
- **合规事实**：Anthropic 不向中国大陆提供服务；国内公开上架的生成式 AI 功能必须用**已备案的国产模型**（DeepSeek/通义/豆包等）并完成 AIGC 登记。因此 AI 层做 `LLMProvider` 协议抽象，Claude 为参考实现，国产模型为上架实现；提示词与 schema 两边共用。
- **端侧**：Apple Foundation Models（约 3B、4K 上下文）适合离线做文本解析/分类/短总结，不做拍照估热量；大陆 Apple Intelligence 可用性未定，不作硬依赖。

## 6. 训练中体验（Watch + iPhone）
- Watch 为主控：开始训练 → 每组一键记组（预填上次/引擎建议的重量与次数）→ 自动起休息计时（T−10s 与 0s 触觉）→ 表冠 30s 步进调整；实时心率；iPhone 上 Live Activity/灵动岛镜像计时（iOS 17+ 镜像会话）。

### 7.4 SwiftData 模式（SetmioData）
**持久化决策**：`@Model` 实体命名 `…Entity`，与 Core 值类型互相映射（`toDomain()` / `apply(_:)`）；引擎、HealthKit 适配、手表、AI 层只见 Core 结构体；SwiftUI 列表/详情页允许直接 `@Query` 实体以获得响应式更新，但凡是交给引擎的数据都先 `toDomain()`。理由：`@Model` 非 Sendable、绑定 `ModelContext`，Swift 6 严格并发下不能跨进 `HealthSampleImporter`（actor）或后台 `@ModelActor`；而完全用仓库层包住 SwiftData 又比 `@Query` 多写很多代码，个人工具不值得。
**实体（V1，18 个）**：父→子 `@Relationship(deleteRule: .cascade)` + 子端 inverse；所有 HK 衍生实体的 `hkUUID` 唯一，重装后 anchor 丢失也能幂等重导。
- Training：`ExerciseEntity`（unique id，`#Index([\.nameZH])`）、`ProgramTemplateEntity`（`daysJSON: Data`，小树状结构不查询就存 JSON，省 4 个实体）、`MesocycleEntity`（`weeksJSON`、isActive 索引）、`PlannedSessionEntity`（`#Unique([mesocycleID, day])`）、`LoggedSessionEntity`（`hkWorkoutUUID` unique、feedback 字段、`sets` 级联）、`LoggedSetEntity`（unique id，`#Index([exerciseID, completedAt])` 供"某动作最近 N 组"查询）。
- Health：`DailyMetricsEntity`（unique day）、`ReadinessScoreEntity`（unique day）、`BodyMeasurementEntity`（`hkUUID` unique、date 索引）、`ImportedWorkoutEntity`（HK 训练与本地会话的对账表，`linkedSessionID?`）。
- Lifestyle：`FoodEntryEntity`(+`items` 级联)、`FoodItemEntity`、`EnergyEstimateEntity`（unique day）、`MedicationEntity`、`DoseLogEntity`（`#Index([medicationID, takenAt])`，`hkDoseEventUUID` 可空唯一）、`PenInventoryEntity`、`SideEffectLogEntity`、`GLP1PlanEntity`（`stepsJSON`）、`UserProfileEntity`/`SettingsEntity`（单例行，`key = "profile"`）。
- 不进 SwiftData：HK anchor（Application Support 文件）、设备令牌（Keychain）、UI 偏好（UserDefaults）、手表训练中日志（手表本地 JSON）。
**版本化与容器**：`SetmioSchemaV1: VersionedSchema`（实体嵌套在枚举内，`typealias` 导出）、`SetmioMigrationPlan`（V2 起加 `.lightweight`/`.custom` 阶段；JSON 血块自带 `schemaVersion` 字段，可不动 SwiftData 迁移而演进）；`ModelContainerFactory.make(inMemory:storeURL:)` 是唯一构造点，`ModelConfiguration(... cloudKitDatabase: .none)` 显式写死（5.1.3(ii) 一行可审）；存储目录文件保护设为 `.completeUntilFirstUserAuthentication`（不是 `.complete`，否则锁屏下的后台投递打不开库）。
**仓库门面**：`@ModelActor public actor SetmioStore`（后台上下文，供 `HealthSyncService` / 镜像接收器调用）：`upsertDailyMetrics`、`upsertReadiness`、`dailyMetrics(from:to:)`、`upsertLoggedSets(_:into:)`（按 id 幂等）、`upsertLoggedSession`、`recentSets(exerciseID:limit:)`、`activeMesocycle()`、`upsertBodyMeasurements`（按 hkUUID 去重）、`markWorkoutImported`、`seedExercisesIfNeeded`。

### 7.5 HealthKit 服务（SetmioHealth）
**类型集**：`HealthTypes.mvpRead` = bodyMass/bodyFatPercentage/leanBodyMass/heartRate/restingHeartRate/heartRateVariabilitySDNN/respiratoryRate/appleSleepingWristTemperature/stepCount/activeEnergyBurned/basalEnergyBurned/workoutEffortScore/estimatedWorkoutEffortScore/sleepAnalysis/`HKSeriesType.heartbeat()`/workoutType；`mvpShare` = workout/heartRate/activeEnergyBurned/workoutEffortScore；`iOS27Read` 在 `#available(iOS 27,*)` 且标识符存在时加 RMSSD；V1 再加 dietary* 与用药事件。RMSSD 不依赖系统类型：`HeartbeatSeriesReader` 用 `HKHeartbeatSeriesQuery` 枚举 RR 间期自算，iOS 26 即可用；若 iOS 27 原生提供则优先系统值。
**并发模型**
| 类型 | 隔离 | 理由 |
|---|---|---|
| `HealthKitAuthorizer` | struct, Sendable | 无状态包装 `requestAuthorization(toShare:read:)` |
| `HealthSampleSource`（协议）+ `HKHealthSampleSource` | Sendable | 伪造 HealthKit 的唯一接缝 |
| `AnchorStore` | actor | 串行化 anchor 文件写入 |
| `HealthSampleImporter` | actor | 同类型不并发导入 |
| `BackgroundDeliveryCoordinator` | final class, Sendable | observer 回调来自任意队列 |
| `DailyMetricsSource` | struct, Sendable | 取样 + 调 Core 的纯聚合 |
| `WorkoutSessionManager`（watchOS） | `@MainActor @Observable final class: NSObject` | 驱动 SwiftUI；HK delegate 回调 `nonisolated` 后跳回主线程 |
| `MirroringSessionReceiver`（iOS） | `@MainActor final class: NSObject` | 解码消息送入 `AsyncStream` |
| `WorkoutWriter` / `MedicationReader` | struct, Sendable / `@available(iOS 26,*)` | 异步写 / 仅 iOS |

**关键签名**
```swift

```
实现要点：`HKAnchoredObjectQueryDescriptor` + `.result(for:)`，anchor 用 `NSKeyedArchiver`（secure coding）存文件，键 `"<kind>#v<anchorSchemaVersion>"`（映射方式变了可强制全量重导）；导入器分页（500）直到不足一页，**每次 sink 成功后才持久化 anchor**；observer 在 `SetmioApp.init` 注册一次（后台唤醒无 UI）。
`DailyMetricsSource` 取 `[前一天 18:00, 当天 12:00]` 内的睡眠/HRV/HR/RR/腕温样本交给 Core 的纯函数 `DailyMetricsAggregation.aggregate`：睡眠窗口 = 首选来源（Apple Watch）的 asleep* 样本，合并间隔 <30 分钟，取最长块；夜间 HRV 取窗口内中位数（抗尖峰），RMSSD 从窗口内心搏序列算；RHR 冻结 = 若 Apple 的 `restingHeartRate` 在 `rhrFreezeHour`(默认 10:00) 前已有则用之，否则取夜间心率第 5 百分位，冻结后不再覆盖；步数/能量用 `HKStatisticsQueryDescriptor(.cumulativeSum)` 日总量（只喂负荷与 TDEE，不影响早晨评分）。
watchOS `WorkoutSessionManager`：`state`(.idle/.preparing/.running/.paused/.ending/.ended/.failed)、`heartRate`、`elapsed`、`mirroringConnected`；`start(plan:)`（`HKWorkoutConfiguration(.traditionalStrengthTraining, .indoor)` → `startMirroringToCompanionDevice()` → `beginCollection`）、`pause/resume`、`end(effort:)`（`session.end()` → `endCollection` → `finishWorkout()` → `WorkoutWriter.writeEffort`）、`send(_:)`、`recoverIfNeeded()`（`recoverActiveWorkoutSession`）；delegate 回调 `nonisolated` 内 `Task { @MainActor in … }`，心率取 `builder.statistics(for:)?.mostRecentQuantity()`。
iOS `MirroringSessionReceiver`：在 `init` 里设置 `store.workoutSessionMirroringStartHandler`，必须在 `SetmioApp.init` 中创建；`messages: AsyncStream<MirroringMessage>`，`send(_:)` 回传 ack/planUpdated/restTimerCommand。
`WorkoutWriter`：`writeEffort(_:for:)`（`HKQuantity(unit: .appleEffortScore(), 1...10)` + `relateWorkoutEffortSample`）、`writePhoneOnlyWorkout`（`HKWorkoutBuilder`）、metadata（`HKMetadataKeyIndoorWorkout`、`com.setmio.sessionID`、`setCount`、`volumeKg`）。`MedicationReader`（iOS 26）：`requestAccess`、`userMedications()`、`doseEvents(since:)`，骨架阶段为返回空的 `@available` 桩，具体查询描述符在 Mac 上对照 WWDC25 "Track medications" 核对。
测试：`FakeHealthSampleSource` 记录授权请求、按类型返回预置样本与递增假 anchor、可触发 observer 回调并断言 completion 恰好调用一次；`HealthSampleImporterTests` 覆盖分页到底、sink 失败不存 anchor、重置后重导、删除 UUID 传播。

### 7.6 算法引擎接口（SetmioCore，均为 struct + `init(config:)` + 纯函数，`now`/`Calendar`/`TimeZone` 作参数传入）
- **ReadinessCalculator**：`ReadinessWeights{hrv, rhr, sleep, load, subjective}`（可配置，默认按 4.1）、`ReadinessConfig{baselineDays 60, rollingDays 7, minimumBaselineDays 14, …}`、`ReadinessInputs{day, history[DailyMetrics ≤60 天], today, weights}` → `ReadinessResult = .score(ReadinessScore) | .insufficientData(daysAvailable, required)`；公式按 4.1；子分按可用分量重新归一，`confidence = min(1, baselineDays/60) × 可用权重`。测试：①30 天基线 HRV 50±5、RHR 55、睡眠 7.5h，今天相同 → 分数在中性带、confidence≈0.5；②近 7 天 HRV 38、RHR 62 → 分数 <45 且 hrv 分量 z 为负；③仅 10 天 → `.insufficientData(10, 14)`；④golden 文件循环断言；⑤聚合测试：睡眠 23:30–07:10，HRV 02:00=45、03:30=55、14:00=30 → `hrvSDNN == 50`（白天样本排除）、`asleepMinutes == 460`，10:00 冻结的 RHR 不被覆盖。
- **ProgressionEngine + E1RMTable + ReadinessModulator**：`ProgressionRule(.doubleProgression | .rtsPercent)`、`ProgressionDecision(.hold(reason) | .increaseLoad(by) | .addSet | .deload(DeloadReason: e1rmDrop/feedback/readinessStreak/mesocycleEnd))`、`MesocycleState{weekIndex, targetRIR, isDeload, weeksTotal}`、`ExerciseHistory{sets(最近在前), feedback, bestE1RMThisMeso}`；`E1RMTable.percentOf1RM(reps:rir:)`（RTS 表插值，Epley 兜底）、`e1RM(load:reps:rir:)`；`ProgressionEngine.plan(prescription:exercise:history:meso:) -> PlannedExercise`（规则按 4.2；减载周组数 60%、重量 −10%、RIR 3–4）；`ReadinessModulator.modulate(_:readiness:)` 只改当天副本（<40：重量 −10%、每动作 −1 组、RIR +1；40–60：最后一个复合动作 −1 组；>85：可选 +1 组标记）。测试：①卧推 8–12 @RIR2，上次 60kg×12/12/12 @RIR2 → `.increaseLoad(by: 2.5)` 且首组 62.5；②e1RM 100→96→94（连续两次低于周期最佳 ≥5%）→ `.deload(.e1rmDrop)`；③`e1RM(100, 5, 2) ≈ 123±1`；④readiness 30 下 4×100kg 深蹲 → 3×90kg，原 `PlannedSession` 不变（Equatable 断言）。
- **RestTimerPolicy**：`duration(after:exercise:next:readiness:)`，默认复合 180s / 孤立 90s，`rir ≤ 1 && reps ≤ 6` 加 30s，低恢复度加 15s，热身 60s。测试：深蹲 5 @RIR1 → 210s；哑铃弯举 12 @RIR2 → 90s；热身 → 60s。
- **EnergyBalanceEstimator**：`EnergyObservation{day, weight?, intakeKcal?, loggedMealsRatio}`；`initialEstimate(profile:weight:age:day:)`（Mifflin-St Jeor × activityFactor）；`update(_:with:)`：EMA 趋势体重 → 窗口内最小二乘斜率 → 观测 TDEE = 平均摄入 − 斜率×ρ → 测量噪声 `R = (300 / max(completeness, 0.2))²` → Kalman 增益更新 `tdee`、`variance`（Q = 50²）；无摄入记录时只更新趋势（细节按 4.3）。测试：①初值 2500±400，14 天体重平、摄入 2200 → 3 次更新后 tdee ∈ 2200…2300 且方差下降；②体重 −0.5 kg/周、摄入 1800 → 收敛到 ≈2350；③completeness 0.3 的增益小于 1.0。
- **GLP1LabelTable / GLP1PlanValidator / GLP1DecisionSupport**：`GLP1LabelTable.loadBundled()`、`drug(_:)`；`HardBlock`（`doseExceedsLabelMax(maxMg)`、`skippedStep(expectedNextMg)`、`escalationTooSoon(daysOnStep, requiredDays)`、`minIntervalViolation(hoursSinceLast, requiredHours)`（翻倍补打也落这里）、`doseNotOnLadder`、`vialVolumeMathUnsupported`、`penInUseExpired(expiry)`）；`GLP1PlanValidator.validate(dose:plan:history:pen:now:) -> Result<Void, HardBlock>`、`buildPlan(for:startingStepIndex:weekday:reminderHour:)`、`nextDue(plan:history:now:calendar:)`；`Advice{kind: .escalate(toMg) | .hold(reason) | .maintenance | .taper | .seekCareNow(reason), rationaleZH[], framing: .discussWithDoctor（唯一取值）}`；`GLP1DecisionSupport.advise(GLP1DecisionInputs{plan, drug, doses, sideEffects, weightTrendPercentPerWeek?, goalReached, now}) -> Result<Advice, HardBlock>`，规则按 4.4/4.5（任一 3 级副作用 7 天内 → `.seekCareNow`；≥2 级 14 天内或依从 <75% → `.hold`；达目标 → `.maintenance`；`.taper` 只在用户主动请求停药评估时返回且不带计算出的减停表），每条路径先过校验器，`HardBlock` 短路。测试：①替尔泊肽 5 mg、在档 35 天、副作用 ≤1、趋势 −0.2%/周、未达目标 → `.escalate(toMg: 7.5)` 且 `framing == .discussWithDoctor`；②在档 20 天 → `.escalationTooSoon(20, 28)`；③计划在 10 mg 时记录 15 mg → `.skippedStep(12.5)`，20 mg → `.doseExceedsLabelMax(15)`；④两针相隔 24 h → `.minIntervalViolation(24, 72)`；⑤瓶装任何剂量 → `.vialVolumeMathUnsupported`；⑥`loadBundled()` 解码 `glp1_labels_cn_v1.json` 含司美 0.25→2.4、替尔泊肽 2.5→15、玛仕度肽 2→6。阶梯表以数据交付（`version/market/updatedAt`），V1 启用前逐条核对国内说明书。

### 7.7 Watch ↔ iPhone 数据流
| 状态 | 归属 | 传输 |
|---|---|---|
| 计划模板、中周期、今日 PlannedSession | iPhone（SwiftData） | 计划变化时 `WCSession.updateApplicationContext(["plan": json, "planVersion": n])`，watch 缓存到文件 |
| 训练中的 LoggedSet | watch 写、phone 镜像 | `sendToRemoteWorkoutSession(data:)`；失败时 `WCSession.transferUserInfo` 兜底 |
| 完成的 LoggedSession | iPhone 为事实来源 | `.sessionEnded` 消息，phone 回 `.ack` 后 watch 清日志 |
| HKWorkout | HealthKit（watch 写入） | HealthKit 自带同步；phone 按 `hkWorkoutUUID` 关联 |
| 休息计时状态 | watch（训练中）；phone 镜像给 Live Activity | `.setLogged` 带 `restSeconds`；phone 启动/更新 Live Activity |

镜像消息信封：`MirroringEnvelope{v, seq, message}`，`MirroringMessage` = `hello / setLogged / setDeleted / sessionEnded / ack / planUpdated / restTimerCommand`，JSON 编码，只传小载荷。
流程：watch `start(plan:)` → 开 `HKWorkoutSession` + `startMirroringToCompanionDevice()` → 系统后台拉起 iOS App（`workoutSessionMirroringStartHandler` 须在 App 启动时同步注册）→ 每次记组先写本地 JSON Lines 日志（fsync）再发送 → phone 按 `LoggedSet.id` 幂等 upsert 并回 ack → 结束时 `finishWorkout()` + 写 effort score + `.sessionEnded`。
冲突与离线：id 在 watch 生成，phone 全部幂等 upsert（镜像与兜底重复投递无害）；训练中 phone 只读，结束后 phone 可编辑并递增 `revision`，watch 的旧重发不会覆盖；watch 离线可用缓存计划或内置"自由训练"独立运行，日志 7 天未 ack 在设置中提示手动处理；watch 崩溃后启动时 `recoverActiveWorkoutSession()` + 日志回放。phone 单独训练时用 `HKWorkoutBuilder` 直接保存。
Live Activity（iOS Widget 扩展，骨架先建、V2 填充）：`RestTimerActivityAttributes.ContentState{endDate, isPaused, pausedRemaining, setLabel, nextTarget}`，运行中用 `Text(timerInterval:countsDown:)` 无需更新；每组最多更新一次；暂停/跳过按钮通过 AppIntent 经镜像通道回传 watch（watch 仍是计时状态的事实来源）。

### 7.8 AI 代理契约（`proxy/`，TypeScript + Hono，可部署到 Cloudflare Workers 或 Node）
原则：规则引擎算数值，代理只做"感知与语言"；iOS 不持有任何模型密钥；代理不保存请求体和图片（只记路由、设备哈希、耗时、token、状态）；`ModelBackend` 接口（`ClaudeBackend` / `DomesticBackend`）是换模型的唯一切点，提示词与 zod schema 与后端无关；Claude 后端必须部署在大陆以外（Workers 或 HK/SG Node），国产后端可部署在境内。
| 路由（均 POST，`Authorization: Bearer <deviceToken>`） | 请求 | 响应 | 限额 |
|---|---|---|---|
| `/v1/devices/register` | `{inviteCode, deviceName, platform}` | `{deviceToken, deviceId}`（只显示一次，存 SHA-256） | 5/IP/小时 |
| `/v1/food/recognize` | `{imageJpegBase64, imageWidth, imageHeight, hints{mealType?, locale:"zh-CN", userNote?, recentFoods?}}` | `FoodRecognitionResult` | 60/设备/天，体积 ≤2 MB，60 s |
| `/v1/food/parse-text` | `{text, locale, hints?}` | `FoodRecognitionResult` | 100/天 |
| `/v1/coach/chat` | `{messages[≤20 轮], context: CoachContext, locale}` | `{replyZH, suggestions[], safetyFlags[]}` | 200/天 |
| `/v1/report/weekly` | `{weekStart, metrics, training, nutrition, medication{adherencePct, sideEffectSummary}}`（只传聚合数值） | `{titleZH, summaryZH, highlights, concerns, nextWeekFocus}` | 7/天，120 s |
`FoodRecognitionResult`：`items[{nameZH, nameEN, portion{amount, unit, gramsEstimate}, kcal{low, best, high}, macrosBest{proteinG, carbsG, fatG}, confidence, needsConfirmation}], overallConfidence, notesZH, model{provider, id}`。错误信封：`{error{code: unauthorized|rate_limited|invalid_request|image_too_large|upstream_refusal|upstream_error|backend_unavailable, message, retryable, retryAfterSeconds?}}`；模型 `stop_reason == "refusal"` → `upstream_refusal`（不可重试）。
Claude 后端（已核对 SDK 文档）：`@anthropic-ai/sdk`，模型 `claude-opus-5-5`；不传 `thinking`（该模型始终开启），用 `output_config.effort`（识菜/解析 `low`，对话 `medium`，周报 `high`，需显式设置，默认是 medium）；结构化输出用 `client.messages.parse({..., output_config: {format: zodOutputFormat(schema)}})` 读 `parsed_output`；图片用 `{type:"image", source:{type:"base64", media_type:"image/jpeg", data}}` 放在文本块之前；稳定系统提示加 `cache_control: {type:"ephemeral"}`；`max_tokens` 识菜 4096 / 对话 8192 / 周报 16000；错误按 `Anthropic.RateLimitError` → `Anthropic.APIError` → 连接错误顺序映射。服务端 refusal fallback（`fallbacks: "default"` + beta 头）留作后续，先处理 `refusal` 停止原因。
鉴权与限流：bearer → SHA-256 → KV 查 `devices:<hash>`；限流键 `rl:<deviceId>:<route>:<yyyy-mm-dd>`（Workers KV 最终一致，个人工具可接受）；密钥 `ANTHROPIC_API_KEY`、`INVITE_CODE` 用 `wrangler secret` / `.dev.vars`。
设备端预处理（`SetmioAI/ImagePreprocessor.swift`）：`UIGraphicsImageRenderer` 重绘（烘焙方向、去除全部 EXIF/GPS），最长边 ≤1536 px，JPEG 0.8，编码后 >1.5 MB 则降到 0.7；照片仅在用户选择时本地保存。
Swift 侧：`protocol LLMProvider: Sendable { recognizeFood / parseMealText / chat / weeklyReport }`，`LLMError` 枚举，`ProxyClient`（URLSession + Keychain 设备令牌 + 错误信封解码 + 可重试错误重试一次），`ClaudeProxyProvider`、`DomesticProvider`（V3 前抛 `providerUnavailable`），`DeviceCredentialStoring`（Keychain 实现 + 内存实现供测试/Linux）。`ContractDecodingTests` 用代理 zod 示例生成的 fixture 做双向契约测试。

### 7.9 隐私与合规
- HealthKit 衍生数据（体重、HRV、摄入、评分、针剂）**只存本地 SwiftData，不开 CloudKit 同步**（App Store 5.1.3(ii) 禁止把健康数据存 iCloud；CloudKit 加密字段是否算 iCloud 无官方答复，视为高风险）。CloudKit 只同步非健康内容（计划模板、动作库、设置）。
- 健康数据如需出设备（多端/备份），走自建后端 + 应用层端到端加密 + 单独同意（Apple WWDC20 明确支持同步到自有服务器）；大陆上架时境内存储，PIPL 把健康数据列为敏感个人信息（单独同意 + 个人信息保护影响评估），>1 万人的敏感信息出境需网信办安全评估。
- 发给 LLM 的只有脱敏后的最小数据：食物照片去 EXIF 并裁剪、数值摘要不含身份信息；HealthKit 数据不进任何分析/广告 SDK。
- 大陆上架清单：ICP 备案（需境内主体或发行方，App Store Connect 填备案号）、法人主体提交（5.1.1(ix)）、生成式 AI 功能用已备案国产模型并做 AIGC 登记、展示药品信息需互联网药品信息服务备案、处方药不得出现购买链接/比价/品牌排名（广告法与互联网广告办法）、任何剂量建议须经合作互联网医院的执业医师。
- 自用阶段最低要求：隐私清单、HealthKit 用途说明、免责声明与"咨询医生"提示照常做，避免以后返工。

## 10. 风险与开放问题
- **Apple 正在进入同一领域**：Series 12/Ultra 4 的 Readiness、Health App 重设计、后续 AI 教练。差异化放在力量训练自动调节、能量平衡、GLP-1 保肌与跨数据统一分析，而不是通用恢复度。
- **HRV 数据稀疏**（旧表每 2–5 小时一次）：Readiness 以夜间数据为主；提供 1 分钟正念"抽查"；换表（Series 12）后重建基线。
- **iOS 27 RMSSD 类型手表是否写入**未证实：代码里按 `#available` 探测，有则用，无则 SDNN 或从心搏序列自算。
- **拍照热量误差大**（混合餐 ~35%）：产品上用区间 + 份量确认 + 用户修正，不承诺精度。
- **Claude 在大陆不可用 / 上架须国产备案模型**：AI 层抽象，提示词与 schema 与模型无关；自用阶段由用户自行选择可用提供方。
- **减肥针决策辅助的法律边界**：自用可做；上架前必须降级为记录 + 提醒 + 医生方案执行，或与互联网医院合作。
- **体重秤生态碎片化**：只走 HealthKit；云麦/Keep 是否写入 Apple Health 未证实，需用户实测。
- **SwiftData + Swift 6 并发**：`@Model` 非 Sendable，跨 actor 只传 Core 结构体或 `PersistentIdentifier`；`@ModelActor` 的写入在 save 前不会出现在主上下文 `@Query`，保持小而频繁的保存；`#Index`/`#Unique` 对可选属性的语义需验证。
- **存储文件保护与后台投递**：`.complete` 保护会让锁屏唤醒时无法读库，用 `.completeUntilFirstUserAuthentication` 并实测锁屏下的 HRV 唤醒。
- **HealthKit anchor 重装后失效**：靠 `hkUUID` 唯一列去重；首次 60 天全量导入可能数十秒，导入器分页（500 条）并显示进度。
- **watchOS 后台**：训练会话保活进程但息屏时 UI 定时器不触发，休息计时触觉需验证后台 `WKInterfaceDevice.play` 是否被抑制，否则用 `UNNotificationRequest` 兜底；镜像发送在手机不可达时会抛错，所以本地日志 + WatchConnectivity 兜底是必需项；`workoutSessionMirroringStartHandler` 必须在 iOS App 启动时同步注册。
- **effort score**：写入需要共享授权；watchOS 11+ 系统可能仍对第三方训练弹自己的强度评分，需验证并避免双重提问。
- **iOS 26 用药 API / Live Activity 暂停显示 / XcodeGen 26 平台字符串**：均隔离在单文件或 `#available` 后，首次在 Mac 生成与真机运行时验证。
- **大陆访问代理**：Cloudflare Workers 可能慢或被阻断，`baseURL` 在设置中可配，备选 HK/SG 的 Node 部署。
- **阶梯表正确性**：GLP-1 剂量/间隔以版本化 JSON 数据交付，V1 启用提醒前须逐条核对国内最新说明书（诺和盈、穆峰达、信尔美）。
- **本容器无 Swift 工具链**：骨架无法在此编译，首次编译在 Mac 上；可选在容器安装 Linux 工具链验证 SetmioCore 的 `swift test`。
- 待确认事实：国内替尔泊肽 15 mg 规格是否上市；先维盈说明书阶梯；玛仕度肽价格；云麦/Keep 秤的 Health 同步。
